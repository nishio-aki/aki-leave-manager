# 🌿 現場が自走する！Google Workspaceを活用した持続可能な有休管理システム

[![YouTube Demo](https://img.shields.io/badge/YouTube-デモ動画を見る-red?style=for-the-badge&logo=youtube)](https://youtu.be/5xC31ppwvsc)

本システムは、単なる有休申請の自動化ではなく、**「人間が行っていた業務をどこまでシステムに移し、どこから人間の判断に戻すべきか」**を設計した業務改善プロジェクトです。
業務フロー、データ構造、承認・例外処理、定期バッチ、通知設計までを一体として設計し、小規模組織で実際に運用可能なコストと複雑性に抑えることを重視しました。

## 💡 2. 開発の背景・動機（なぜ作ったか）

小規模な現場では、有休管理が属人化・アナログ化しているケース少なくありません。実際に自身の有休残日数を確認しようとした際、以下のような課題に直面しました。

* **情報の不透明さ:** 「担当者に確認しないと分からない」「特定の権限者しか把握できない」という状況による高い確認コスト。
* **属人化の弊害:** 従業員が自身の残り有休日数を確認できない状況や、担当者によって所要時間が異なる属人性の存在。

大掛かりなエンタープライズ向けSaaSや複雑なクラウドインフラ（AWS/GCPの本番構築など）は、小規模な現場の規模感やコスト面においてオーバースペックです。何より「現在の自身のスキルセットやリソースに合わせた現実的かつ持続可能な実装」を重視しました。過剰な仕組みを排し、日常使い慣れたツールで「持続可能で属人性を排除した仕組み」を構築しました。

## 🛠️ 3. 使用技術

過剰なインフラコストをかけず、小規模組織やコストを抑えたい環境でも堅牢に稼働することを想定しています。

* **バックエンド / ロジック:** Google Apps Script (GAS)
* **データストア:** Googleスプレッドシート（マスター管理・一時保存）
* **トリガー / 通知:** Gmail（承認要請・タイムアウト時のエスカレーション通知）
* **インターフェース:** Googleフォーム（申請・照会）
* **運用自動化:** GASの定期実行トリガー（自動有休付与・失効監視・タイムアウト検知）

## 🗂️ 4. データ構造（スプレッドシート設計）

### ① 社員マスタ
* **A列（社員ID）:** 一意の識別子（例: `EMP001`）
* **B列（名前）:** 社員名
* **C列（入社日）:** 所属部署
* **D列（ステータス）:** 自動付与の基準日判定に使用
* **E列（メールアドレス）:** 各種アラート・通知の送信先

### ② 付与履歴
* **A列（付与ID）:** `社員ID_YYYYMMDD` で生成される一意のキー
* **B列（社員ID）:** 紐づく社員
* **C列（付与日） / D列（有効期限）:** 有効期間の判定（FIFOの対象範囲）
* **E列（付与日数） / F列（消費済日数）:** 残日数計算のソース
* **G列・H列（通知フラグ）:** 6ヶ月前・1ヶ月前の通知済み管理

### ③ 取得履歴（トランザクション）
* **A列（タイムスタンプ）:** 申請日時
* **B列（社員ID）:** 申請者
* **C列（取得日） / D列（取得区分）:** 全休・半休の判定
* **E列（メールアドレス）:** 申請者メール
* **F列（取得ID）:** フォーム連携用の一意なキー（例: `G-YYYYMMDD-HHmmss`）
* **G列（ステータス）:** `承認待ち` / `承認済み` / `調整依頼中` / `【要】事務対応`

## ⚙️ 5. 主要機能

有休管理における「申請・承認」「照会」「定期的な運用保守」の全プロセスをカバーしています。

1. **インターフェースの一元化**
   * 従業員からの「申請」「照会」から上司側の「承認・却下」に至るまで、すべてのユーザー操作をフォームおよびメール経由に一本化。
2. **申請・承認ワークフロー（エンドツーエンド）**
   * 申請を受けスプレッドシートへ一時書き込み後、上司へ承認要請メールを自動送信。未返信時のタイムアウト検知・担当事務へのエスカレーション機能も実装。
3. **有休照会機能**
   * 従業員自身が自身の残日数や取得状況をいつでも確認できる仕組みを提供し、確認コストを大幅削減。
4. **自動有休付与・失効監視（定期バッチ）**
   * 勤続年数や法規に基づく自動付与、有効期限や法定要件（年5日取得義務）にかかるリスクを自動検知・通知。

## 📝 6. 試行錯誤と設計の変遷（Development Story & Design Choices）

実際の開発・運用において直面した壁と、それをどのように乗り越えたかという設計の変遷です。

### ① データ構造の試行錯誤（スナップショットからトランザクションへ）
* **直面した壁:** 当初は失効期限別にデータを分けるため「状態保存用の列を2セット用意して管理する」アプローチを検討し、検証に約2週間を費やす。しかし後に「有休の失効ロジック」が完全に抜け落ちていることが発覚。
* **設計の刷新:** 単なる静的なスナップショット管理から、時系列で履歴を正しく追える「変形トランザクション設計」へと刷新。

### ② インターフェースとデータ入力の刷新（属人性の排除）
* **課題:** スプレッドシート直接運用を想定していたが、確認コストやシートの直接編集によるフォーマット崩壊・誤操作リスクが発生。
* **アプローチ:** すべての入力を「Googleフォーム」へ一本化。さらに申請内容がメールで控えとして手元に残るUXにブラッシュアップ。

### ③ 法的要件（時季変更権）を考慮した非同期承認フローの導入
* **課題:** 当初はFIFO（先入れ先出し）で即時書き込みを想定していたが、労働基準法における使用者の「時季変更権」を考慮し仕様変更。
* **仕様:** 一度「承認待ち」状態にして上司へ打診メールを送信。時季変更の場合は上司の「具体的な理由」と「避けてほしい期間」を部下に自動通知し、再調整が可能な仕様に。

### ④ 承認プロセスのタイムアウト・エスカレーション管理
* 申請から24時間以上経過しても承認がない場合、上司へ自動で催促しつつ、担当事務へも代替処理要請メールを行うエスカレーション機能を実装。

### ⑤ 失効・取得義務アラートの多段階実装
労働基準法の「年5日取得義務」や権利失効リスクを防ぐため、多段階のアラートを実装：
* **条件1（6か月前アラート）:** 期限6か月前で残日数 10日以上 の場合
* **条件2（1か月前アラート）:** 期限1か月前で残日数 5日以上 の場合
* **条件3（法定要件アラート）:** 「1年で5日以上の消化」を達成していない場合

### ⑥ 通知の最適化（アラート疲労の防止）
* **設計の転換:** 週次レポートの全件送信は人間の監視コストやノイズ（アラート疲労）につながるため、「平時は通知せず、エラーや要対応の検知時のみ即時通知する（**例外検知型**）」へ簡素化。

### ⑦ 心理的アプローチによるUX向上とデータ品質の担保（ゲーミフィケーションの実装）
* **設計の背景:** 一般的な事務手続きの通知では労働者の行動変容（有休取得）まで促せない。そこで「有休を取るためのナレッジと空気感」が自然と循環する仕組みを設計。
* **実装アプローチ:** あえてハードボイルドな世界観（独自の演出）を導入し、無機質な事務連絡を「有休取得を応援される体験」へ昇華。さらに、この世界観の徹底により、ユーザーがふざけた入力をしづらい心理的抑止力を生み出し、データ品質も同時に担保。

### ⑧ データ一意性の担保（行数依存の脱却）
* スプレッドシートの行数依存によるIDズレ・重複リスクを防ぐため、実行時の**「タイムスタンプ」ベースによる一意のID生成方式**に変更。

## 🛡️ 7. 現場の安定稼働を支える技術的こだわり（Design Policies）

ただ動くだけのコードではなく、実務の運用事故を防ぎ、長期間ノーメンテナンスで堅牢に稼働させるために以下の設計ポリシーを徹底しています。

* **浮動小数点誤差の徹底排除（丸め処理）**
  * JavaScriptの仕様上発生する小数点の計算ズレ（例：半休 `0.5` の足し引きによる微小なゴミ）を防ぐため、残数計算やFIFOエンジンの消費処理の随所に `Math.round()` を用いた桁数調整（小数点第2位までの丸め）を組み込み、誤作動を防止。
* **トランザクションの保護（排他制御）**
  * 同時申請や複数チケットの更新時に発生するデータの競合や上書き事故を防ぐため、書き込み処理には `LockService` を導入。
* **例外検知によるフェイルセーフ（`throw new Error`）**
  * 有休残高の不足など、データ不整合や運用上の致命的なエラーが発生した際は、曖昧に処理を進めず確実に処理を中断し、システムエラーとして即座に検知できる設計を採用。
* **パフォーマンスと負荷の最適化**
  * 重い処理（外部APIやメール送信など）はループの外側で制御し、アラート通知はノイズを防ぐ「例外検知型（要対応時のみ即時送信）」に絞ることで運用コストを軽減。

## 🚀 8. 今後の改善点・チャレンジしたいこと

持続可能な運用（Sustainable Ops）に向けて以下の改善を計画しています。

* **運用ドキュメント（Runbook）の整備:** 初期設定手順やトラブルシューティングをMarkdownで詳細にまとめ、誰が引き継いでも運用できるようにする。
* **スプレッドシート列構造の動的マッピング化（ハードコーディングの脱却）:** 
現在の実装ではメンテナンスコストと小規模運用のシンプルさを優先し、列インデックスのハードコーディングを採用している。将来的なスプレッドシートのレイアウト変更や拡張性（複数人開発へのスケール）を考慮し、起動時に1行目のヘッダー名から列番号を動的に解決する createColumnMap 方式へのリファクタリングを計画している。
